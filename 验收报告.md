## Part 2: Specification Comparison & Summary (Spec 对比总结)

### 2.1 Overview & Objective

In this laboratory exercise, two requirement documents were evaluated:
1. **Source A (Initial Spec):** The requirement specification generated automatically by the Huawei Cloud CodeArts (码道) agent based on initial natural-language prompts.
2. **Source B (Reference Spec):** The standard lab manual specification provided by the course instructors.

The objective of this comparison is to evaluate differences in architecture, database design, API consistency, and functional scope, assessing how the AI-generated specification aligns with academic lab standards.

---

### 2.2 Detailed Comparison Matrix

| Evaluation Dimension | Source A: CodeArts Initial Spec | Source B: Lab Manual Reference Spec | Practical Engineering Impact |
| :--- | :--- | :--- | :--- |
| **Database Architecture** | Recommended an Object-Relational Mapping (ORM) layer such as Flask-SQLAlchemy with database migration workflows. | Prescribed a lightweight, direct `sqlite3` interface using raw SQL schemas and custom dictionary row factories. | The raw `sqlite3` approach eliminated heavy dependency overhead, enabling rapid testing via `init_db.py` without migration lockups. |
| **Data Schema & University Context** | Outlined generic e-commerce entities (`users`, `products`, `orders`) with basic fields (`id`, `title`, `price`, `description`). | Required explicit campus-context attributes: `dorm_building`, `campus_zone`, `student_id`, and `condition_rating`. | Integrating campus-specific attributes enabled intuitive filtering by dorm and student identity directly on listing cards. |
| **API Response Standards** | Relied on bare HTTP status codes ($200, 400, 404, 500$) returning unstandardized payload bodies. | Enforced a unified response envelope: `{"code": 0, "message": "...", "data": {...}}` with specific business error codes ($401, 409$). | Axios interceptors were configured to uniformly parse business codes, redirecting unauthenticated requests smoothly to login. |
| **Transaction State Machine** | Assumed a binary status model: `is_sold = True / False` reflecting immediate digital checkout. | Enforced a three-stage offline transaction lifecycle: $\text{Available} \rightarrow \text{Reserved} \rightarrow \text{Completed}$, with cancellation rollbacks. | Modeled real-world campus trade dynamics where items must be locked for inspection prior to offline cash/transfer completion. |
| **Media Handling & Placeholders** | Relied purely on external image URLs with no fallback or local upload logic. | Required simulated campus image storage or robust asset fallback mechanisms. | Added CDN-backed placeholders in seed scripts and implemented client-side image error handling (`@error` SVG fallbacks). |
| **Input Validation Constraints** | Did not define strict text constraints or length caps. | Defined business validation constraints: $Title \le 50$, $Description \le 300$, $Comment \le 200$. | Client-side reactive character counters and schema validation prevent database overflow errors. |

---

### 2.3 Synthesis of Differences & Key Takeaways

1. **Contextual Specialization:**  
   The initial AI-generated specification produced a generic, commercial marketplace architecture. In contrast, the course reference specification grounded the platform into a university campus environment by enforcing student verification attributes (`student_id`, dorm locations, campus zones). Adapting the AI spec to the reference manual was essential to make the application feel authentic to students.

2. **Offline Transaction Workflow:**  
   Commercial platforms often assume instant payment gateway integrations (e.g., Stripe, WeChat Pay). For campus second-hand trades, transactions occur primarily face-to-face. The lab manual's requirement for a multi-state lifecycle ($\text{Available} \rightarrow \text{Reserved} \rightarrow \text{Completed}$) ensures that reserved goods are locked against competing buyers until both parties meet offline.

3. **API Standardization:**  
   The reference specification emphasized standardized API design with explicit business status codes. This consistency streamlined frontend state management, allowing Pinia stores to handle errors and toasts without complex per-route conditional checks.

4. **Conclusion:**  
   CodeArts successfully scaffolded the baseline architecture and CRUD operations, while the lab manual provided the domain-specific business rules. Reconciling both resulted in an efficient, production-ready, and cohesive web application.
